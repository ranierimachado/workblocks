# Automated scheduling through documents/

Workblocks exchanges files with a scheduling service on the linked computer. The service does not need HTTP access to localhost. This channel is available while the computer, DDEV and the Workblocks feed worker are running.

## Local workflow

`~/Sites/dev.sh start workblocks` starts the app and one feed worker. `stop workblocks` stops both. The worker checks every 15 seconds and requires two observations at least two seconds apart with unchanged size, modification time and content hash before processing a file. Typical pickup takes 15–30 seconds.

The app writes a current export after each committed planner change and when the worker starts. `outbox/current.json` is the unchanged [version 2 contract](feeding-contract-v2.md), with no extra export-only properties. A temporary file is atomically renamed over `current.json`, so readers never see partially written JSON. If the workspace has no initial plan, there is no export until a plan is imported.

All paths below are relative to the configured feed directory, which defaults to the project’s ignored `documents/` folder locally:

```text
outbox/current.json
inbox/<timestamp>-<description>.json
inbox/applied/<filename>.json
inbox/applied/<filename>.json.result.json
inbox/rejected/<filename>.json
inbox/rejected/<filename>.json.reason.txt
inbox/pending/<filename>.json
inbox/pending/<filename>.json.reason.txt
```

The sidecar name appends `.result.json` or `.reason.txt` to the complete input filename. Conflicting archived filenames with different content receive a hash suffix; use a fresh timestamped filename for each submission to avoid collisions. Non-JSON files in the inbox are ignored. Only direct `inbox/*.json` files are scanned, never the archive subdirectories.

Filenames must begin with an ASCII letter or digit and contain only letters, digits, periods, underscores and hyphens, ending in `.json`. Keep filenames below 220 characters and files below 2 MB. Symbolic links are not accepted. Files are processed oldest first, with filenames breaking modification-time ties.

## What applies automatically

A valid version 2 document must match the current workspace ID and revision. It can automatically:

- Move work between dates, slots and carryover, preserving block IDs.
- Change notes, week metadata, standing-template allocations or priority display names/ranks.
- Add new priorities and blocks. Every new block needs a new UUID; missing IDs are not supported.
- Change the duration or assigned priority of an unfinished block, keeping its block UUID.
- Split unfinished work using `split_from`, conserving the parent’s minutes.

An explicit duration reduction is a supported edit and can reduce planned hours without deleting a block. This follows the automatic-feed policy; the applied result records the before/after minutes and update details.

## What waits for approval

A valid feed is moved to `inbox/pending/` if it:

- Omits any existing unfinished block ID, including a carryover block.
- Removes any active priority, even one without allocated blocks.
- Uses version 1, which is always a destructive reset.

Version 2 cannot edit completed history. Unsupported completion fields and attempts to reuse a completed UUID as unfinished work are invalid and rejected, rather than applied. Completed work retains its existing history.

Open **Plan imports → Pending feeds → Review and approve** to inspect the reason and full preview. Apply only after reviewing the deletion/reset details. Approval rechecks the exact file contents, schema and semantic rules, plus the workspace revision observed when it was held. It fails if the workspace moved on; the stale file is rejected with an explanation. This also protects version 1 pending resets, which do not carry their own revision fields.

**Discard** archives the feed in `rejected/` with `discarded by user`, without changing the schedule. A stale pending feed is labeled in the UI and should be regenerated by the scheduler.

## Invalid/outdated feeds

Invalid JSON, contract errors, unknown references, wrong workspace IDs and outdated revisions go to `inbox/rejected/`. Their reason sidecar contains the validation message and current revision. They never change planner state.

Infrastructure errors such as a failed database backup or an unavailable archive directory are logged and retried; they are not treated as permission to bypass checks. The worker and UI/CLI share the same planner write lock. Once one file advances the revision, another file from the old revision is rejected.

A receipt is committed in the same database transaction as an applied import. If the process stops after that commit but before archiving or writing the result, the next pass finishes delivery from the receipt without importing the feed again. Duplicate files with the same name and bytes are not reapplied. Physical backups, import history and rollback behavior remain active.

The result sidecar has:

```json
{
  "import_id": "a4b1a696-813a-4578-b51a-a3653ca51e33",
  "previous_revision": 5,
  "new_revision": 6,
  "applied_at": "2026-11-06T20:30:00+00:00",
  "summary": {
    "mode": "update",
    "plan_name": "My plan",
    "changes": {
      "added": [],
      "removed": [],
      "moved": [],
      "updated": [],
      "split": []
    }
  }
}
```

`summary` is the full existing preview response; the example above abbreviates its other count and metadata fields. The archive JSON itself preserves the original submitted bytes.

## Instructions for Claude or another file producer

1. Read `documents/outbox/current.json` immediately before planning the change.
2. Preserve `workspace_id`, `base_revision`, existing block IDs, carryover and all unrelated work. Produce a complete version 2 snapshot, not a patch.
3. Make the requested changes. Use new UUIDs for new blocks and `split_from` for new split children. Include explanations in the affected week’s `changes`.
4. Validate against `contracts/plan-v2.schema.json`. Do not omit IDs or add completion/history fields.
5. Write `documents/inbox/<timestamp>-<description>.json`. Prefer writing a non-JSON temporary name and renaming after the write is complete.
6. Poll for that filename in applied, rejected or pending for up to about 90 seconds. Read the sidecar and report one short result to the user.
7. If outdated, read `outbox/current.json` again and reapply the requested change once. If it fails again, stop and report the problem.
8. Never edit/archive files in applied, rejected or pending; never approve a pending feed yourself.

There is no export, upload or approval click for non-destructive updates. Deletions and resets still wait for the user.

## Operations

Configuration in `backend/.env`:

```dotenv
WORKBLOCKS_FEED_ENABLED=true
# Optional. Defaults to the project's documents/ directory.
# WORKBLOCKS_FEED_DIRECTORY=/absolute/path/to/exchange
```

Commands from the project root:

```bash
ddev exec php artisan feed:watch --interval=15
ddev exec php artisan feed:process
ddev exec php artisan feed:status
~/Sites/dev.sh logs workblocks feed
```

The watch/process commands use a singleton worker lock, so starting another instance cannot create a second processor. `feed:process` performs one observation/processing pass; a new file must be observed unchanged in a later pass before it is processed. The browser refreshes the board and pending list automatically every ten seconds.

Production Docker Compose includes a `feed` service and persists its exchange directory at `/data/documents` in the same named volume as the database. The app and worker must share that directory, the database, and the planner lock. The compose file shares the lock directory between them. A cloud scheduling service still needs a way to read/write those hosted files; the Mac-linked desktop bridge alone does not provide remote-droplet access.

Turning `WORKBLOCKS_FEED_ENABLED` off stops automatic exports and prevents the watch/process commands from running. Restart the app/worker after changing environment settings. Tests explicitly disable live feeding and use isolated temporary directories for file-exchange cases.
